# Base app UI design

Treat the selected base screenshots and their verified visual analysis as the visual foundation. Preserve the approved core journey and feature scope. Distinguish visible app UI from promotional poster framing. Missing screens and states are proposed designs, not observed behavior.

For each proposed screen, identify its reference screenshot and describe the visual anchors to preserve: primary content position/proportion, navigation placement, action hierarchy, control grouping, typography scale, spacing and color roles. State necessary adaptations for approved enhancements. Unobserved screens should reuse the established visual language and explicitly describe their uncertainty.

Define a small reusable set of visual tokens and component patterns from the actual evidence: surfaces, accents and selected states, text roles, gaps, corners, icon weight, app bars, option rows and dialogs. Do not replace base tokens with a default workspace palette. Explicit user appearance changes remain authoritative documented deviations. Avoid importing branding, advertisements, account/paywall flows or unselected source features.

Fit enhancements into the base's existing hierarchy. For a tree-focus base, keep the tree and timer central; task selection, sound controls and goal progress are supporting controls. The forest/history should visibly carry completed sessions. Describe clear inactive, running, completion and abandonment states; successful/failed outcomes remain visible until acknowledged. Specify portrait, compact-height/landscape, keyboard and larger-text adaptations while keeping the same primary actions recognizable.

Before finalizing, compare the proposed screen descriptions and visual contract to the attached reference images. Correct unexplained changes in composition, navigation, density or visual emphasis. Record deliberate deviations in the design rather than silently redesigning the product. Do not claim that proposed design or source inspection establishes final APK visual fidelity.
